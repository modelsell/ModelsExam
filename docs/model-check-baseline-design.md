# Claude 多类型基线与测试集

> 本文件保留 v7 设计依据。当前六道能力题、可选 Bedrock 专项及预算见 [v19 核心能力检测设计](model-check-capabilities.md)；当前基线选择和 Token 台账见 [提示词与缓存检测](model-check-token-audit.md)。

本次实现：报告版本 7；基线由管理员审阅检测历史后手动设置；自动匹配当前管理员最近最多 50 份基线。类型可以填写 `anthropic`、`aws`、`ccmax`、`kiro` 或其他文字标签。标签是操作者提供的来源分类，不是系统认证结论。

## 操作流程

1. 打开模型检测页面，填写渠道或 Base URL、Key、型号。
2. 选择“基线采集”，检查请求预算后手动开始。完整预设最多 76 次请求，10 分钟总时限、单请求 90 秒；不会自动重试。
3. 审阅模型字段、能力题、采样分布和请求记录。完成的当前版本报告可“设为基线”，标记来源类型；存在明确型号冲突或检测未完成时不能设置。
4. 对其他可信型号、供应商类型、不同采样时间重复上述步骤。不要因为渠道名称含“官方”就赋予它官方可信度。
5. 后续页面发起的检测自动冻结并加载当前可用基线。要比较回答分布，待测方也要开启“行为指纹测试集”；普通快速检测仅提供已有证据的对照。

同一报告重复设置返回原基线，不能悄悄替换原数据。每份历史报告内保留当时使用的所有基线快照；后来增加新基线不会改变旧报告。原请求 ID、响应头及完整诊断证据通过来源报告追溯，不递归复制历史基线。

## 测试集及预算

| 分组 | 内容 | 额外请求 | 可用依据 |
| --- | --- | ---: | --- |
| 现有完整检测 | 协议结构、流式、工具、参数边界、多轮、图像、PDF、Thinking、缓存与重复请求 | 21 | 当前协议兼容性与渠道行为 |
| 能力题 v1 | 下表 12 道客观题 | 12 | 正确率、逐题答对/答错模式 |
| 行为指纹 v1 | 数字、字母、颜色、中文动物偏好，各采样 10 次，交错执行 | 40 | 分类回答直方图及分布相似度 |
| 生成性能 | 相同数字序列任务，3 次流式生成，每次最多 512 输出 token | 3 | 首字时间、端到端输出速率与同条件耗时 |

能力与指纹请求明确设置 `thinking: {type: "disabled"}`，不设置 temperature、top_p、top_k 或高 effort；选择题最多 64 输出 token，能力题最多 512。这样避免将新型号官方不接受的非默认采样参数用于采集。成本由真实上游请求产生，不是免费基准测试。

### 行为指纹 v1

| 分类 | 合法输出 | 重复数 |
| --- | --- | ---: |
| number | 十进制 1–10 | 10 |
| letter | A–J，大小写归一 | 10 |
| color | red / blue / green / yellow / purple / orange | 10 |
| animal | 猫 / 狗 / 马 / 兔 / 虎 / 鹿 | 10 |

按轮交错四种任务，减轻时间漂移影响。只能接受完整 `end_turn`、有效协议结构、合法选项、最终发送参数摘要匹配的回答。解释性文本、未知选项、截断、拒答、错误或参数变化仍计入尝试数，但不充当合法分布样本。权限拒绝或 429 停止当前新增测试集，避免继续消耗。

双方都需要四类各至少 10 个有效样本才计算分布得分；样本不足显示未评估，不补零、不套用其他型号的数据。原始自由文本不进入指纹库，只保存允许选项的计数。

## 对照与评分

- **兼容性分**：保留原有评分；新增采集任务作为独立观察，不加入其分母。
- **能力正确率**：本次答对数 / 有效评分题数 × 100，同时显示覆盖题数。截断、参数变化和传输问题不算答错。
- **答题模式一致度**：双方同题、同版本、同参数的有效结果中，答对/答错状态相同的比例。双方都答错也属于模式相同，所以该指标不是能力分。
- **协议行为一致度**：对可比较的系统遵从、流式、工具、输出边界、图像、PDF、Thinking、缓存等已评分项目计算相同比例。型号字符串、消息 ID、代理头和用户填写的类型标签不进入相似度。
- **分布相似度**：四类回答分布的平均 Jensen–Shannon divergence（log2，范围 0–1），展示 `100 × (1 − 平均 JSD)`。100 表示这批样本的经验分布相同，不表示真实性为 100%。
- **候选类型**：依据分布相似度排序，距最高分小于 5 分的类型共同展示。5 分是保留相近候选的展示规则，没有经过型号识别准确率校准。无分布数据时，不用协议分强行识别类型。
- **性能**：同探针、同最终参数摘要的有效请求做配对，至少 3 对才给出当前/基线耗时比中位数。固定性能任务要求输出不少于 64 token 且至少两个文本事件，才统计首字时间和输出 token/完整耗时；此速率包含首字等待，不等同于纯解码速度。网络、缓存和负载不参与型号身份推断。

## 证据质量和采集建议

1. 对需要辨别的每个“类型 × 实际型号”分别采集，优先使用自己控制的官方 Anthropic 或 AWS 账户作为可信来源；代理基线如 CCMax、Kiro 保持人工标记。
2. 同条件在多个时间点重复采集，保留多个快照。当前 v1 每类 10 次只是初步分布，不应宣称达到论文中的样本量或误判率。
3. 留出独立检测轮次验证同型号波动、不同型号重叠；若多类型都得高分，保留不可区分结论。模型版本、Thinking、effort、缓存状态和注入的系统提示均可能改变表现。
4. 后续扩展题库应先增加难度覆盖、变体与独立验证，再评估区分度。不要仅为了制造差异而选择对某型号不公平的参数。
5. 当供应商故意模仿响应行为，或发现测试题后特判路由，有限黑盒探针不能提供密码学证明。需要自有账户的 AWS 调用记录等独立依据，才能进一步追溯实际调用。

## 存储与访问

- `model_check_baselines` 使用 GORM，兼容 SQLite、MySQL 和 PostgreSQL；基线仅属于创建管理员。
- 创建接口只接受历史报告 ID 和类型，基线内容由服务端读取已脱敏的历史记录。不能上传自造报告或伪造“已验证”属性。
- 每份快照最多 32 KiB，自动匹配最近 50 份，总量控制在历史报告和 SSE 的既有限制内。
- 本次交付不预填伪造的“官方模型基线”，也不自动对收费渠道采样。真实对照数据由用户审阅手动采集产生。
