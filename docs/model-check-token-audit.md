# 提示词与缓存计数检查（报告 v14 / TokenAudit v7）

2026-09-16：提示词注入检查改为三次最小请求的输入用量检查，完全不依赖手动基线或 CountTokens。没有明显超额给 100 分，超额越多分数越低。评分是经验检测结果，不是无注入概率。旧版报告和旧客户端的 v8 流程保持兼容。

## 开始前选择对照基线

新检测在表单中先选已有基线类型（如 `anthropic`、`ccmax`、`kiro`），再选该类型与当前型号兼容的已保存记录。类型下有多份记录时默认选保存时间最新的一份，操作者可改选具体记录。允许不对照，以便采集新的基线。

前端发送 `baseline_id` 与 `baseline_type`，服务端在模型请求发出前校验记录归属、类型和型号，将该份快照固定进报告 `baselines`，选择信息保存在 `options`。不根据测试结果自动换成最相近的基线。缺失、其他用户或型号冲突的选择返回 400，不开始检测。新客户端未选择时不加载基线；旧客户端显式 `compare_baselines: true` 且无选择字段仍兼容原自动对照。

Token 计数台账中的**基线总输入**来自所选快照的同题、相同请求参数样本，取这些样本的中位数；**基线差值 = 本轮总输入 - 基线总输入**。两边的总输入均包含普通输入、缓存写入与缓存读取。64 Token 经验预算、CountTokens 以及本次缓存冷写量都不再作为该列的基线参照。提示词注入评分仍按下文的独立规则计算。

- 性能与指纹的独立重复题可合并为同题样本；最小提示词题允许旧 `floor_a` 与新 `minimal` 名称，但完整请求指纹仍须一致。
- 缓存冷写和每次读取分别对比，不能混合；带随机前缀的跨次请求内容不同，完整请求指纹不同就留空，不强行假定同题。
- 旧基线缺题、缺合法用量或参数不同时，台账显示无参照及原因，保留原始实测值。
- 旧快照主动省略的指纹用量可以从同用户、相同报告 ID／版本／型号的原历史只读补取，只保留精简用量和请求指纹；不覆盖快照已有样本，不修改数据库。原历史不可用或补全超过 32 KiB 时使用原快照。
- 新 v14 精简检测保存全部请求的精简计数，包括指纹样本；全部 50 次请求的测试快照约 19.6 KiB，仍受 32 KiB 上限约束。

报告中的独立基线列表和“基线差异”模块已移除，顶部保留本次选定记录的摘要，具体 Token 差值在台账展示。手动“保存为基线”作为完成后的折叠操作保留。过程、历史和 HTML 导出都读取本次冻结的快照，不以日后新保存的基线替换历史参照。

## 三次最小请求

不携带 system、tools、历史消息或显式缓存控制，独立发送三次同样的请求：

```json
{
  "model": "<本次检测型号>",
  "max_tokens": 128,
  "thinking": {"type": "disabled"},
  "messages": [{"role": "user", "content": "Return only the word PONG."}]
}
```

固定题目和参数，让经验容许量只适用于这个短请求。每次只记录响应的总输入 Token，不判定回答是否为 PONG，不调用 CountTokens，不增加长题、已知 system 或提示词提取测试。

`总输入 = input_tokens + cache_creation_input_tokens + cache_read_input_tokens`

普通输入必须是有效计数；缓存字段按既有协议解析规则处理。无法获得合法总输入时保留不可用行，不伪造零值。每次发完更新过程报告，结束后评分；权限、限流、取消沿用既有停止规则。

## 不依赖基线的评分

内置 `64 Token` 的经验容许量，给短文本、消息封装、模型 tokenizer 和正常计量差异留出空间。**64 是本系统为减少误报选择的产品参数，不是官网承诺的正常上限，也不是精确预期输入量。** 它覆盖本地观察到的 15 和 43 Token 短请求；不用用户保存的基线，不按平台或型号标签提高门槛。

每条有效样本总输入为 `A`：

- `A <= 64`：100 分，表示未见明显额外输入。
- `A > 64`：`round(100 × 64 / A)`，最多 99 分；疑似追加量估算为 `A - 64`。
- 总分是有效轮次得分的四舍五入均值；任一轮超额，总分最多 99。全部轮次都参与，不剔除异常轮。
- 展示疑似追加量均值、最大值、超额轮次，以及总输入中位数/范围。差值只是超出经验预算的用量，不表示精确注入长度。
- 完成后至少一条合法计数即可评分，同时单列有效轮数及覆盖率：一条为 33%，两条为 66%，三条为 100%。没有合法计数则显示未取得用量，不当作零输入或无注入。
- 已知本地修改了 system、tools 或消息内容时，明确报告改写，无法估算其长度时不伪造分数。型号字段、平台线索和输出是否严格回答 PONG 不作为输入量评分门槛。

| 三轮总输入 | 总分 | 每轮疑似追加量均值 |
| --- | --- | --- |
| 43、43、43 | 100 | 0 |
| 128、128、128 | 50 | 64 |
| 256、256、256 | 25 | 192 |
| 7078、7078、7078 | 1 | 7014 |
| 43、43、7078 | 67 | 2338 |

历史数据只读回放验证：此前“官 key”记录的最小题为三次 43，按新规则为 100；最近“claude kiro”三次 7078，按新规则为 1。渠道名称是用户标签，不是独立认证。回放没有调用付费接口，也没有修改历史评分。

## 缓存与预算

缓存沿用两组独立随机前缀，每组一次冷写、三次读取，共 8 次请求。读取只与本组有效冷写对照；保留未命中、重复写入及缺少计数的情况，现有缓存评分与性能采样规则不变。

v14 精简流程核心 10 次；指纹 +20、缓存 +8、提示词 +3、PDF +1、视觉 +1、Bedrock 专项 +7。默认开启指纹/缓存时 38 次；全部可选项开启最多 50 次（此前 65 次）；关闭指纹、核心加缓存和提示词为 21 次。总时限仍为 10 分钟。v15 将能力扩展为 12 题、最多 13 次请求，核心/默认/全开预算分别变为 17/45/57。v16 移除旧六题，仅运行最新六题（能力最多7次），并默认关闭偏好采样，核心/默认/全开预算为11/19/51。v17 移除偏好采样和主动 Bedrock 边界探针，预算为11/19/24。v18 保持偏好题移除，恢复默认关闭的可选 Bedrock 专项（最多+7次），核心/默认/全开预算为 **11/19/31**，默认组合加 Bedrock 为26；核心加缓存及提示词为22。v19 增加四组固定输入长度的 usage 检查，核心/默认/全开预算为15/23/35；默认加 Bedrock 为30。详见 [Usage Token 计数检查](model-check-usage-tokens.md) 和 [能力检测设计](model-check-capabilities.md)。

## 过程、历史与验证边界

过程、历史、HTML/打印及 JSON 使用同一份报告证据。新提示词数据保存在 TokenAudit v7，评分标识 `input_budget`；逐轮记录预算、用量、超额和分数。旧 v12 报告保留 `input_consistency` 的原始基线对照，不回算、不修改历史数据。能力和性能继续使用所选基线比较，v17 不再收集或展示派生偏好相似度。

主报告只展示已选择或有历史采样的提示词/缓存卡片。真正选择但未获得可用数据的项目仍显示原因；未勾选项目不展示空卡。缓存只使用正式 `cache_assessment` 分数，缓存命中率作为证据，不再额外展示可能与一致性分矛盾的命中状态100分。

100 分表示本次有效样本没有明显超出经验预算，不能排除预算内的小量追加、等长内容替换或 usage 伪造。超额可能来自平台模板、路由封装或计量差异，不自动等同恶意提示词注入。需要确认实际追加内容时，应对照可信上游账号的请求日志。
